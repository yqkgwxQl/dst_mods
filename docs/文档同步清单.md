# 文档同步清单

> 目的：每次 `git push` 之前，确认仓库里**所有文档**都与代码一致，没有过期内容。
>
> 触发时机：任何一次准备提交之前；发版之前必须完整走一遍。

---

## 一、同步范围

| 文档 | 内容来源 | 什么时候必须更新 | 检查方式 |
|---|---|---|---|
| `README.md` | `mods/` 下模组的实际状态 | 增删模组、改数值/配方/科技、发版 | 人工通读 |
| `docs/MOD测试手册.md` | 实测结论与踩过的坑 | 新增测试方法、起服方式变化、新坑 | `check_docs.ps1` + 变更记录 |
| `docs/工作区约定.md` | 目录职责与落盘规则 | 新增目录、新增例外规则 | `check_docs.ps1` |
| `docs/本机环境.local.md` | 本机路径、游戏版本、账号 | 换机器、游戏更新、路径变化 | 人工核对（不入库） |
| `mods/<mod>/setting/mechanic_design.md` | 代码里的数值与机制 | 改 `TUNING`、改机制、调平衡 | 逐项对照代码 |
| `mods/<mod>/setting/setting_description.md` | 世界观与视觉语言 | 改设定、改配色、换素材目录 | 人工通读 |
| `mods/<mod>/setting/annotated/*_annotated.lua` | 精简版 `.lua` | **每次改代码** | `sync_annotated.ps1` |
| `mods/<mod>/modinfo.lua` | 版本号、描述、变更注释 | 每次发版 | 与存档头部、设计稿状态核对 |
| `tools/` 里的脚本说明 | 脚本实际行为 | 改脚本参数/用法 | 人工核对脚本头部注释 |

> `<mod>` 指具体模组目录，例如 `mods/blade_of_the_ruined_king`。

---

## 二、改动盘点（新增 / 删除 / 修改）

**每次提交前先做**：把整个项目的改动列出来，逐条判断“是否需要同步文档”。

### 1. 命令

```powershell
# 最直观：所有新增 / 删除 / 修改（含未跟踪）
git status --porcelain=v1

# 分类盘点 + 同步提示（推荐）
powershell -ExecutionPolicy Bypass -File tools\scripts\check_changes.ps1

# 辅助：看改动量
git diff --stat
git diff --cached --stat
```

### 2. 按改动类型判断要不要同步

| 改动类型 | 典型文件 | 需要同步 |
|---|---|---|
| **修改代码** | `modmain.lua`、`scripts/**/*.lua` | 跑 `sync_annotated.ps1`；数值/机制变了就改 `mechanic_design.md` |
| **新增代码文件** | 新 prefab、新 FX prefab | 加进 `PrefabFiles`/`Assets`；补 `mechanic_design.md`；跑同步脚本 |
| **删除代码文件** | 删 autotest、删旧 prefab | 全仓搜引用（`git grep`），清 `modimport`、`Assets`、文档 |
| **改版本号** | `modinfo.lua` 的 `version` | 存档头部（脚本自动）、`mechanic_design.md` 状态、README、手册 |
| **改文档** | `README.md`、`docs/*.md` | 跑 `check_docs.ps1`；检查链接、版本、状态描述 |
| **新增/替换素材** | `anim/*.zip`、`*.png`、`*.scml` | 更新 `setting_description.md` 素材清单；README 状态 |
| **删除素材/目录** | `setting/asset/` | 全仓搜旧路径；更新所有引用它的文档 |
| **改工具脚本** | `tools/*.ps1` | 同步脚本头部注释 + 本清单的「自动命令」一节 |
| **未跟踪文件** | 临时脚本、备份目录 | 确认是否入库；临时产物加入 `.gitignore` |

### 3. 判定原则

1. **删除必搜引用**：任何被删除的文件/目录，先 `git grep -n "<文件名>"`，确认没有文档还在指它
2. **新增必问记录**：新增文件后问自己“有没有哪份文档需要提到它”，尤其是 README、素材清单
3. **改数值必对照**：只要碰了 `TUNING`，就逐项核对 `mechanic_design.md`
4. **未跟踪必确认**：`??` 文件要么入库，要么进 `.gitignore`，不能长期悬空
5. **重命名按“删除 + 新增”处理**：两边都要清引用、补记录

## 三、三条自动命令

在仓库根目录执行：

```powershell
# 1) 改动盘点（新增 / 删除 / 修改 + 同步提示）
powershell -ExecutionPolicy Bypass -File tools\scripts\check_changes.ps1

# 2) 文档结构与链接检查
powershell -ExecutionPolicy Bypass -File tools\scripts\check_docs.ps1

# 3) 把代码改动同步进注释存档
powershell -ExecutionPolicy Bypass -File tools\scripts\sync_annotated.ps1
```

**期望输出：**

- `check_changes.ps1` → 列出各类改动与建议动作（逐条处理）
- `check_docs.ps1` → `汇总：PASS=x  FAIL=0  WARN=0`
- `sync_annotated.ps1` → 每个存档都打印 `code identical: True`

只要出现 `FAIL` 或 `False`，先修好再提交。

## 四、版本号一致性（最容易漏）

一个版本号会出现在四个地方，**必须同时改**：

| 位置 | 示例 |
|---|---|
| `modinfo.lua` 的 `version` | `version = "1.0.2"` |
| `setting/annotated/*_annotated.lua` 头部 | 由同步脚本自动读 `modinfo.lua`，不用手改 |
| `setting/mechanic_design.md` 顶部状态行 | `状态：P0 / P1 已完成` |
| `modinfo.lua` 底部的变更注释 | `1.0.2 机制版本（日期）` |

另外，`docs/MOD测试手册.md` 末尾的「变更记录」表要补一行——**只记手册本身的变化**，不记模组版本。

## 五、README 特别提醒

`README.md` 是访客第一眼看到的内容，**优先级最高，也最容易过期**。

当前已知过期项（写这份清单时的状态，已于 2026-11-11 修正，留作反面例子）：

- 模组路径写的是 `mods/mod_test_2` → 实际是 `mods/blade_of_the_ruined_king`
- 伤害写 50 → 实际 54（低理智最高 +25%）
- 配方写「树枝 ×2 + 燧石 ×1」→ 实际「噩梦燃料 ×2 + 金块 ×1 + 燧石 ×1」
- 科技写「无」→ 实际炼金引擎
- 状态写「配方与数值仍在调整」→ 实际 P1 已完成

发版前逐条核对，改完再提交。

## 六、提交前检查清单

- [ ] 已跑 `tools\scripts\check_changes.ps1`，每一类改动都有对应的同步动作
- [ ] 被删除的文件/目录已 `git grep` 过，文档和代码里没有残留引用
- [ ] 新增文件已确认“入库还是忽略”，并补了必要的文档记录
- [ ] `check_docs.ps1` 输出 `FAIL=0`
- [ ] `sync_annotated.ps1` 两个存档都输出 `code identical: True`
- [ ] `modinfo.lua` 版本号 == 设计稿顶部状态描述的阶段（如 v1.0.2 ↔ P1 完成）
- [ ] `README.md` 的模组名、路径、数值、配方、科技、状态与实际一致
- [ ] `mechanic_design.md` 的数值与 `TUNING.BLADE_OF_THE_RUINED_KING` 逐项一致
- [ ] `MOD测试手册.md` 的「变更记录」补了本次改动
- [ ] `git status` 里没有意外文件（`*.glb`、`autotest.lua` 应被忽略或已删除；`*_annotated.lua` 是入库的生成物，需先跑同步脚本）
- [ ] 本次改动没有留下「计划中」「待实现」但实际已完成的描述

## 七、一次完整流程

```text
改代码 / 改素材 / 改文档
  → 跑 tools\scripts\check_changes.ps1（盘点改动，逐条判断要不要同步）
  → 跑 tools\scripts\sync_annotated.ps1（同步注释存档）
  → 改相关文档（设计稿 / README / 手册 / 素材清单）
  → 跑 tools\scripts\check_docs.ps1（结构检查）
  → 人工过一遍「提交前检查清单」
  → git add / commit / push
```

## 八、常见漂移与后果

| 漂移 | 后果 |
|---|---|
| 改了 `TUNING` 没改 `mechanic_design.md` | 下一个人按文档调平衡，越调越偏 |
| 删了 `autotest.lua` 没删 `modimport` | 进世界直接报错，mod 被禁用 |
| 删了目录没清文档引用 | 文档链接失效，新人按旧路径找不到文件 |
| 新增素材没记录 | 下次换贴图时找不到来源和规格 |
| 版本号只改 `modinfo.lua` | 存档头部版本与实际不符，回滚时对不上号 |
| README 停留在旧模组 | 访客以为装的是另一个 mod，反馈全错位 |
| 手册写了「待验证」但实际已验证 | 重复劳动，浪费时间 |

## 九、备注

- 本清单本身也属于「文档」，脚本或流程变化时同步更新
- `本机环境.local.md` 被 `.gitignore` 排除，只在本机生效，不参与仓库同步
- 注释存档 `*.annotated.lua` 是否入库由项目决定；无论哪种，**同步命令都要跑**
